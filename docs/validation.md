# aether — проверка и план реализации

Статусы и порядок задач ведутся только в [tasks.md](tasks.md). Этапы ниже описывают техническую приёмку, а не отдельный реестр выполнения.

Локально выполняются только ограниченные тесты без обучения: схемы, синтетические тензоры, маленькие forward-проходы, mock-optimizer и протокол. Реальные optimizer steps, обучающие smoke tests и проверки восстановления обучения — только в удалённом платном Colab. Полные веса, GPU-профилирование и качество модели также проверяются в Colab. «Локальный стенд» в порогах задержки означает контролируемый тест рядом с вычислительным процессом, а не разрешение запускать большую модель или обучение на текущей машине; для живого удалённого разговора отдельно учитывается сеть.

## 1. Принцип

Проверки должны различать корректность программы, совместимость весов и качество обученной модели. Успешный тест формы тензора не доказывает разборчивость речи; приятный голос не доказывает правильность ответа.

## 2. Проверки без больших весов

Использовать маленькие размеры сети и искусственные данные.

| Проверка | Что обнаруживает |
|---|---|
| Разбиение PCM на случайные пакеты | Потерю отсчётов и неверное накопление кадров |
| Delay → undelay на уникальных индексах | Перепутанные каналы, off-by-one и ошибки хвоста |
| Изменение будущего входа | Нарушение каузальности прошлых выходов |
| Teacher-forced streaming и batch forward | Расхождение кешей и масок |
| Reset и новая сессия | Перенос состояния |
| Две чередующиеся сессии | Смешивание состояний между пользователями |
| Протокольный round trip | Ошибки endianness, длины и sequence |
| Переполнение и disconnect | Неограниченные очереди, утечки и зависшие worker |
| Маски loss | Обучение по padding и недействительным позициям |

Сравнение streaming и batch выполняется с одинаковыми начальными условиями и без случайного семплирования. Допуски определяются по dtype. Проверка каузальности исключает изменения, которые законно влияют на выход из-за объявленного выравнивания.

## 3. Проверки с весами

1. Строгая загрузка всех параметров.
2. Проверка соответствия токенизатора и специальных ID.
3. Audio encode/decode на речи, тишине и шуме.
4. Контрольные logits на фиксированном входе при наличии эталонного артефакта.
5. Сравнение покадрового и непрерывного выполнения кодека с учётом padding и хвоста.
6. Разборчивая генерация на офлайн-сценариях.
7. Проверка свободной генерации после любого дообучения.

Побитовое совпадение не требуется между разными GPU и kernel-реализациями. Существенное расхождение должно быть объяснено, а не скрыто расширением допуска до произвольного значения.

## 4. Измерение времени

Разделять четыре величины:

- **Compute step:** encode + temporal + depth + decode одного шага.
- **Pipeline latency:** путь известного входного кадра через транспорт, буферы и обработку до доступности связанного выходного кадра. Связь определяется инструментированием индексов, а не угадыванием по речи.
- **Response gap:** от размеченного окончания пользовательской реплики до начала осмысленного ответа.
- **Yield latency:** от начала явного перебивания до прекращения слышимого ответа.

Latency не измеряется вычитанием несинхронизированных часов двух машин. На локальном стенде используется общий monotonic clock или внешняя запись входа и выхода. Длительности GPU измеряются корректными GPU timers.

На каждом стенде фиксировать минимум: GPU, CPU, RAM, драйвер, версии, dtype, число сессий, режим сети, размер пакета и длительность прогона. Публиковать p50/p95/p99, количество наблюдений и холодный старт отдельно от прогретой работы.

Начальные инженерные цели: compute p95 < 80 мс; pipeline p50 ≤ 300 мс и p95 ≤ 500 мс на согласованном локальном стенде. Это цели проекта, пока не подтверждённые измерениями. Для response gap и yield latency сначала собрать распределения; пороги приёмки утвердить до сравнения кандидатов.

## 5. Диалоговый набор

Не менее 100 сценариев с разделением по категориям:

| Категория | Ожидаемое поведение |
|---|---|
| Короткий вопрос | Релевантный завершённый ответ |
| Пауза внутри вопроса | Отсутствие систематического преждевременного ответа |
| Исправление числа или имени | Использование исправленного значения |
| Явное перебивание | Уступка слова и учёт новой реплики |
| Короткое «угу» | Отсутствие обязательного обрыва ответа |
| Два говорящих одновременно | Сохранение входа и устойчивость генерации |
| Тишина | Отсутствие бесконтрольного бесконечного монолога |
| Шум | Измеренная деградация и отсутствие сбоев |
| Указание в начале разговора | Проверка удержания в пределах контекста |
| Разрыв и повторное соединение | Новое чистое состояние |

Для каждого сценария хранить длительность, ожидаемые признаки, разметку событий и версию набора. Повторять стохастические испытания минимум на трёх seed. Для сравнения вариантов использовать те же сценарии и seed.

## 6. Качество

Содержательные показатели: правильность факта или решения, соблюдение явных ограничений, учёт исправления, удержание контекста. Аудиопоказатели: разборчивость, артефакты, тембр, темп и естественность пауз. Диалоговые показатели: преждевременные ответы, успешные перебивания, ошибочные уступки и зависания.

Автоматическая транскрипция может использоваться для подсчёта ошибок, но сама ошибается. Часть записей проверяют люди; оценка не должна зависеть только от одного автоматического судьи. Категории с маленьким числом примеров не объединяются в убедительный общий процент без указания размера выборки.

## 7. Этапы и условия перехода

### M0 — Python-каркас

Созданы `pyproject.toml`, `uv.lock`, пакет и CLI, валидируемые конфигурации и CI. `uv sync --locked` и CPU-проверки проходят на чистом окружении. Модельный комплект и целевое оборудование зафиксированы либо явно блокируют M2.

### M1 — вычислительные контракты

Маленькая модель проходит формы, каузальность, кеши, delay/undelay, reset и loss masks. Протокол проходит пакеты произвольной длины и ошибочные сообщения.

### M2 — офлайн-голос

Комплект весов загружается строго. Кодек и генератор дают проверяемый аудиовыход. Есть манифест запуска, профиль памяти и отчёт по базовым сценариям. Отсутствие разборчивой речи блокирует переход к демонстрации продукта.

### M3 — живой full-duplex

Python-клиент одновременно передаёт и воспроизводит звук. Прогретая сессия не накапливает очередь. Переподключение очищает состояние. Проверены паузы, перебивания и предел контекста. Измерения сохранены.

### M4 — контролируемое дообучение

Обучение возобновляется из checkpoint, сохраняет замороженные параметры и корректно экспортирует результат. Содержательное улучшение подтверждено на независимых данных, а голосовые регрессии проверены.

### M5 — дальнейшее развитие

Новый язык, более сильная текстовая основа, длинные сессии и масштабирование получают отдельные конфигурации и критерии. Оптимизация производительности не объединяется с изменением обучающих данных в одном несравнимом эксперименте.

## 8. Формат отчёта

Каждый отчёт содержит цель, конфигурацию, среду, хэши артефактов, набор сценариев, размеры выборок, сводные метрики, ссылки на разрешённые диагностические записи, ошибки и решение о следующем этапе. При провале целевого порога сохраняется фактический результат; статус не подменяется формулировкой «почти работает».
